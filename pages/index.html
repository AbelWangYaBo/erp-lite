采购质检怎么闭环

v2 审计曾发现「处置只是打标签」的断头路：不合格批次不冲应付、不扣库存。v3 的处置是真实业务动作——货动、账动、留痕。

purchase下 PO（资质拦截）
→
admin审核（不得自审）
→
warehouse收货 · 批次待检
→
qc → qa录入检验 → 复核放行
→
production领料 · 完工（成品再送检）
→
salesSO · 出库 · 退货回检
→
finance核销 · 冲回 · 对账 · 盘点

不合格批次处置两条路，均账务联动：退货 → 红字流水 + 冲应付 + 冲 PO 已收量（订单回 partial 可重收）； 报废 → 清批次现存 + 损失金额留痕。销售退货则把批次送回待检、冲减应收—— 纠错一律走反向单据，无物理删除。

两条贯穿全局的硬规则

不靠人自觉，靠系统 400 拦截。admin 也没有豁免。

不得自审 规则 A

  • PO / SO / MO 审核、资质审核与撤销、检验复核
  • 操作人 ≠ 单据创建 / 录入人，违反直接拒绝
  • 制单与审批强制分离，职责分离落在代码里

质检双段制 规则 B

  • qc 录入检项与建议结论 → qa 复核判定放行
  • 原料批次与 MO 完工成品批次统一走此链路
  • 成品不再「完工即合格」，pending 不可领料出库

闭环五要素

  • 状态流转可达终点 · 数量金额自动联动
  • 审计留痕（who + role + 字段前后值）
  • 前端入口 + 下一步指引 · 单据全程可点击互跳

角色工作台

  • 登录首页即待办：待审 / 待检 / 待放行 / 待核销
  • 库存三口径：合格 / 待检 / 不合格分列展示
  • 操作成功提示「下一步轮到谁」

本地完整运行

前后端分离：FastAPI + SQLAlchemy + Alembic + SQLite（dev）/ PostgreSQL（prod）；Vue 3 + Element Plus + Vite。

# 后端（默认 SQLite，先迁移建表再灌幂等种子）
cd backend
uv sync
export DATABASE_URL=sqlite:///./erp-dev.db
uv run alembic upgrade head
uv run python ../scripts/seed.py
uv run uvicorn erp_lite.main:app --reload --port 8100

# 前端（dev 代理 /api → localhost:8100）
cd web
npm install
npm run dev
# 打开 http://localhost:15173 —— 登录页有八账号一键填入

# 全链路冒烟（94 断言，八角色接力）
uv run python ../scripts/smoke_v3.py
